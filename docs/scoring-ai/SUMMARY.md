## 무엇을 만들었나

**관광지 여행 난이도를 객관 지표로 수치화하는 규칙 엔진.** 다낭권 15곳을 상·중·하(+보류)로 판정하고, 등급마다 어떤 근거·규칙으로 나왔는지 남긴다.

```
python -m src.scoring   # 근거 통합 → 등급 산정 → 검증 보고서
```

## 핵심 설계 (3줄)

1. **근거 등급**: A 실측(GPS 보행 궤적) > B 지도·공식 사실(OSM 보행로·계단·케이블카, 운영사 정보, 기후) > C 리뷰 집계. 차원마다 가장 높은 등급의 근거로 판정, 낮은 등급은 교차 확인
2. **차원 5개**: 보행 거리, 피할 수 없는 오르막·계단, 대체 이동수단, 더위 노출, 혼잡
3. **판정은 규칙, LLM은 검증**: 오르막 '상' + 대체수단 없음 → 무조건 '상'. 대체수단이 오르막을 대신하면 한 단계 낮춤. 더운 실외 + 오르막이면 한 단계 높임. 근거가 없으면 '하'가 아니라 '보류'

## 결과 (현재)

| 등급 | 관광지 |
|---|---|
| 상 | 오행산, 미선 유적지 |
| 중 | 바나힐*, 호이안 구시가지, 미케 해변, 용다리, 한시장, 호이안 야시장 |
| 하 | 영흥사, 다낭 대성당, 참 조각 박물관, 아시아파크, 하이반 고개 |
| 보류 | 누이탄타이 온천, 껌탄 코코넛 마을 (근거 부족) |

\* 바나힐은 지도 경계 매칭 전이라 보행 거리 과소 측정 가능 → 재산정 예정

## 믿을 수 있나 (검증)

- **LLM-as-a-judge 교차 검증**: 서로 다른 모델 2개(Claude, GPT)가 같은 근거만 보고 독립 채점
  - 엔진 vs judge 일치 10/15, 11/15 · judge끼리 8/15 · 두 judge 합의 시 엔진 일치 7/8 · 2단계 이상 차이 0건
  - → 엔진은 평가자 평균에 가깝고, **LLM에게 등급을 맡기면 모델마다 흔들린다**(규칙 엔진을 쓰는 이유)
- 리뷰 키워드 정밀도: 계단 약 90%, 혼잡 약 70% (직접 읽고 확인)

## 데이터 현실 (멘토 질문 "어디서 구하나"에 대한 답)

| 데이터 | 확보 | 한계 |
|---|---|---|
| Google Places | 15곳 식별, 리뷰 주제 언급 수 | 리뷰는 장소당 5건(공식 API도 동일) |
| Tripadvisor 리뷰 | 13곳 × 150건 | 시연용(약관상 운영 불가) |
| OSM 공개 GPS 궤적 | 실제 보행 궤적 3곳 사용 가능 | 시내 관광지는 차량 궤적뿐 |
| OSM 지도·고도 | 진행 중 | 동남아 태그 희소 |
| 공식 사실 | 15곳 대체수단·실내외 | 계단 수는 1곳만 |

**운영 시**: 외부 스크래핑 대신 하나투어 자체 후기·가이드 입력(검수 화면)으로 같은 엔진을 돌린다.

## 팀이 결정할 것

1. 기준값(보행 1·3km, 오르막 15·60m, 계단 50·200개)이 괜찮은지
2. 동선 담당이 쓸 출력: `data/scoring/grades.json`의 `grade`, `dimensions`, `rules_fired`
3. 사람 기준셋: 팀원 2명이 15곳을 직접 판정해 엔진과 비교 (마지막 검증 단계)
