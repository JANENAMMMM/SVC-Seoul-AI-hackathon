# ScoringAI 설계안 v0.2 (검토용)

> 담당: 남재은 · 브랜치 `JANENAMMMM/scoring-ai` · 상태: **팀 검토 요청**
> 범위: 관광지 1곳의 정보를 입력받아 **관광 난이도(상·중·하) + 근거**를 산출해 DB에 저장한다.
> 대상: 동남아 1개 도시, 관광지 10~20곳 (도시 미정)
> v0.2 변경: v0.1의 7개 차원은 "리뷰로 다 알 수 있다"는 전제였고 현실적으로 수집이 안 된다. **실제로 구할 수 있는 데이터 기준으로 차원을 다시 짰다.**

## 0. 검토 요청 사항 (이것만 보면 됨)

| # | 결정 필요 | 제안 |
|---|---|---|
| 1 | 평가 차원 | **핵심 4개**(고저차, 보행 규모, 더위 노출, 휴식 가능성) + **보조 2개**(대기, 노면, 근거 있을 때만) |
| 2 | 데이터 원칙 | 리뷰에 의존하지 않는다. **측정 가능한 공개 데이터(지형·지도·기후) 먼저**, 텍스트(블로그)는 보정용 |
| 3 | 점수 | 차원별 0~3 → 코드 가중합 → 0~100 부담 지수 → 상·중·하. LLM은 텍스트 근거 해석만 |
| 4 | 검증 | 대상이 10~20곳이므로 **전 관광지를 팀이 직접 검수**(기준셋) → 자동 산정과 일치도 보고 |
| 5 | 확장 계획 | 데이터 없는 항목은 하나투어 가이드·MD 입력(L3)으로 채우는 구조를 시연 |

## 1. 현실성 검토: 무엇을 실제로 구할 수 있나

### 1-1. v0.1의 문제

- **Google Places API는 장소당 리뷰를 최대 5건만 반환**(알려진 제한, 공식 문서로 재확인 필요)하고, 리뷰 필드는 최상위 요금 SKU다. Google Maps 리뷰 크롤링은 약관 위반 소지가 있다 → "리뷰 30건 이상의 언급 비율"은 만들 수 없다
- 노면·벤치·진입 거리는 동남아 지역 지도 데이터에 거의 없다
- 대기 시간(혼잡도)은 Google 공식 API에 없다
- 멘토 지적과 같은 문제: **"정보가 있으면 다 할 수 있다"는 전제에서 출발했다**

### 1-2. 실제로 쓸 수 있는 데이터

| 데이터 | 무엇을 알 수 있나 | 접근성 | 비용 |
|---|---|---|---|
| **고도 데이터** (Open-Meteo Elevation, Google Elevation API) | 입구와 주요 지점의 **고도차(m)** | 좌표만 있으면 항상 가능 | 무료~저가 |
| **OpenStreetMap** (Overpass API) | 관광지 **부지 면적**(폴리곤), 계단(`highway=steps`, `step_count`), 케이블카·엘리베이터, 부지 내 카페·식당 | 주요 관광지는 폴리곤이 대체로 있음. 계단 수는 일부만 | 무료 |
| **Google Places API** | 좌표, 유형(`types`), 운영 시간, 평점 수, 휠체어 접근 입구(`accessibilityOptions`), 주변 카페·식당 검색 | 안정적 | 유료(호출당) |
| **기후 데이터** (Open-Meteo Archive) | 월별 **체감 온도·습도** | 항상 가능 | 무료(비상업) |
| **네이버 블로그 검색 API** | 한국인 후기 **검색 결과 수**와 요약문(`total`, `description`) | 하루 25,000회 | 무료 |
| **여행사 상품 일정표** (공개 페이지) | 관광지별 **체류 시간**("약 2시간") | 대표 관광지는 대부분 있음 | 수작업 수집 |
| 현지 가이드·MD (L3) | 전 항목 | 하나투어 협업 | — |

> 원칙: **측정값 > 텍스트 신호 > 유형 기본값**. LLM의 사전 지식만으로 매긴 점수는 근거로 인정하지 않는다.

## 2. 평가 차원 (v0.2)

### 2-1. 차원과 데이터 매핑

| 구분 | 차원 | 측정 방법 | 주 데이터 | 0 / 1 / 2 / 3 기준 (초기 가정) |
|---|---|---|---|---|
| 핵심 | **고저차** | 입구 ↔ 주요 지점 고도차, 계단·케이블카 유무 | 고도 API, OSM | <5m / 5~20m / 20~50m / 50m+ (케이블카·엘리베이터 있으면 −1) |
| 핵심 | **보행 규모** | 부지 면적 + 상품 일정표 체류 시간 | OSM 폴리곤, 여행사 일정표 | 체류 <1h·소규모 / 1~2h / 2~3h / 3h+·대형 부지 |
| 핵심 | **더위 노출** | 방문월 체감 온도 × 실외 비율 | Open-Meteo, Places 유형 | 실내 / 실외·체감<30℃ / 실외·30~35℃ / 실외·35℃+ |
| 핵심 | **휴식 가능성** | 부지 내·인접 카페·식당·실내 시설 수 | Places 주변 검색, OSM | 다수 / 몇 곳 / 1곳 / 없음 |
| 보조 | 대기 | 블로그 "줄/대기/웨이팅" 신호 | 네이버 블로그 API | 신호 약함 0 ~ 강함 2 (최대 2) |
| 보조 | 노면 | 블로그 "모래/미끄러움/비포장" 신호, OSM `surface` | 네이버, OSM | 신호 있을 때만 +1 |

- 근거: 계단 오르기 6.8 MET vs 평지 보행 3.5 MET(2024 Compendium) → 고저차를 가장 큰 요인으로. 고령층 관광지 불편 1위 경사·계단 23.1%(경기연구원 2024). 등산 난이도는 고도차×거리로 산정(NPS)
- 동남아 고온다습 환경에서 고령자 열 취약성(NUS Heat-Health Hub) → 더위 노출을 핵심 차원으로
- 휴식 간격 50~100m 권장(UK Inclusive Mobility)은 측정 불가 → "쉴 수 있는 시설 수"로 대체

### 2-2. 블로그 텍스트 신호 (리뷰 대체)

```
부담 신호 = total("{관광지} {부담 키워드}") / total("{관광지}")
예: total("바나힐 계단 힘들") / total("바나힐")
```

- 네이버 검색 결과 **건수**만 쓰므로 본문 크롤링 없이 계산 가능
- 키워드 사전은 차원별로 고정 (대기: 줄·웨이팅·대기 / 노면: 모래·미끄·비포장 / 고저차 보정: 계단·오르막·언덕)
- `description` 요약문 상위 N건은 LLM이 읽고 "실제로 부담을 말하는지"만 판정 (광고·반어 걸러내기)
- 한계: 건수는 노출 알고리즘 영향을 받음 → **보정용**으로만, 핵심 차원 점수를 ±1 이상 바꾸지 않음

### 2-3. 합산 (코드)

```
부담 지수 = 100 × Σ(가중치 × 점수) / (3 × Σ가중치)
가중치 초안: 고저차 3 · 보행 규모 3 · 더위 2 · 휴식 2 · 대기 1 · 노면 1
등급: 0~33 하 / 34~66 중 / 67~100 상
예외: 고저차 3 이면서 케이블카 없음 → 무조건 '상'
```

### 2-4. 근거 수준과 "모를 때"

| 수준 | 내용 | 해커톤 |
|---|---|---|
| L1 | 관광지 유형별 기본값 | O |
| L2 | 측정 데이터(고도·면적·기후·시설) + 블로그 신호 | O |
| L3 | 가이드·MD 입력 (최우선, 확정 시 고정) | 검수 화면 |

- 차원마다 `source_level` 저장. L1뿐인 차원은 ±1 범위로 넓혀 표시 → "정보 부족"이 화면에 보임
- 데이터가 없으면 없다고 표시한다. LLM이 빈칸을 추측으로 채우지 않는다

## 3. LLM이 하는 일 (최소화)

| 단계 | LLM 역할 | 이유 |
|---|---|---|
| 관광지 유형 분류 | Places `types` + 설명으로 실내/실외·유형 판정 | 규칙으로 커버 안 되는 유형 |
| 블로그 요약문 판정 | "이 글이 실제로 부담을 말하는가" 이진 판정 | 키워드만으로는 광고·반어 구분 불가 |
| 근거 설명 문장 | 차원별 점수의 이유를 사람이 읽는 문장으로 | 챗봇·UI에서 사용 |
| 2차 검토 (judge) | 측정값·신호·점수를 보고 이상치 지적 | 사람 검수 우선순위 정하기 |

> 점수 계산·등급 결정은 전부 코드. LLM-as-a-judge는 **"판정자"가 아니라 "검토자"** 로 쓴다 (판정을 맡기면 근거 없는 점수와 루브릭 드리프트가 생긴다: RULERS 2026, MT-Bench 2023)

## 4. 파이프라인

```
관광지 목록(10~20곳, 이름·좌표)
   │
   ├─ 고도 API ─────────┐
   ├─ OSM (면적·계단·시설)─┤
   ├─ Places (유형·주변)──┼─▶ 차원별 측정값 ─▶ 코드: 0~3 변환 ─▶ 가중합 ─▶ 지수·등급·범위
   ├─ 기후 (월별 체감) ───┤                        ▲
   └─ 네이버 블로그 신호 ─┘── LLM 요약문 판정 ─────┘ (보정 ±1)
                                                        │
                                       LLM 2차 검토 ─▶ 이상치 → needs_review
                                                        │
                                       DB 저장(draft) ─▶ 팀/담당자 검수 ─▶ confirmed
```


## 6. 검증 (멘토 지적 "현실과 맞는가"에 대한 답)

1. **팀 기준셋**: 대상 10~20곳 전부를 팀원 2명이 블로그·영상·여행사 일정표를 보고 직접 상·중·하 판정 → 사람 간 일치도
2. **자동 vs 사람**: 등급 일치율, 차원별 가중 카파. 불일치 건은 원인(데이터 부족 / 가중치 / 기준값)을 표로 정리
3. **보정**: 불일치 원인에 따라 기준값·가중치 조정 → `rubric_version` 0.3
4. **발표 산출물**: "자동 산정이 사람 판정과 N/20 일치, 불일치 M건은 원인과 함께 검수 대기" 표 1장

| 현실과 어긋나는 상황 | 처리 |
|---|---|
| 데이터 없음 (L1뿐) | 범위 확대 + "정보 부족" 표기 + 검수 대기 |
| 자동 산정과 사람 판정 불일치 | 검수 대기, 원인 기록 → 기준값 보정 자료 |
| 시기별 차이 (우기·성수기) | 더위·대기 차원만 `visit_month`별 계산 |
| 여행 후 체감 차이 | 체감 피드백 누적 시 재검수 요청 |
| 담당자 수정 | `confirmed` 고정, 자동 재산정이 덮어쓰지 않음 |

## 7. 멘토 피드백 대응

| 멘토 지적 | v0.2 대응 |
|---|---|
| 계단·언덕·대기 정보를 **어디서 어떻게** 구할지 (발표 피드백) | 차원별 데이터 출처를 측정 가능한 공개 데이터로 고정 (1-2, 2-1) |
| 러프한 외부 정보를 자체 기준에 매칭해도 정확하지 않다 (발표 피드백) | 텍스트는 보정 ±1만. 핵심 점수는 측정값에서 (2-2) |
| 상·중·하 기준이 현실을 얼마나 반영하나 (발표 피드백) | 전 관광지 사람 기준셋과 일치도 보고 (6) |
| 현실과 안 맞을 때 처리 방법 (발표 피드백) | 상황별 처리표 (6) |
| 일정 배치는 가이드 역량 (발표 피드백) | L3 가이드 입력 최우선 (2-4) |
| 관광지 내부 보행량이 빈칸 (조윤곤 멘토) | 부지 면적 + 상품 일정표 체류 시간으로 근사 (2-1) |
| 데이터 부족은 실행 계획으로 설명 (이도경 멘토) | 없는 데이터 목록과 L3 협업 계획 (1-1, 2-4) |
