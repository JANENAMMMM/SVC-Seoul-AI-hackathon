# 반걸음 — 고객 여행과 MD 작업실 시연

브랜치 `feat/interactive-trip-workspace`는 최신 `origin/develop` (`f6ce34e`)에서 만들고 기존 `feat/final-mockup`의 목업 커밋을 fast-forward로 반영했습니다. 고객 여행 화면에 펼쳐진 선택 버튼을 넣고, MD가 예시 일정을 편집하는 작업실을 추가했습니다. Scoring AI는 진행 중인 1단계 작업이며 이번 UI에서 평가 완료를 가정하지 않습니다.

## 실행

이 작업 디렉터리의 저장소 루트에서:

```bash
uv run python mockup/serve.py
```

http://localhost:8129/mockup/ 접속. 기존 `api.main:app`의 프로필 API를 재사용하고 정적 파일은 `mockup/`와 디자인 시스템만 제공합니다. 루트 `.env`나 저장소 전체를 정적 서버로 노출하지 않습니다. 서버 시작·프로필 정규화는 DB 접속이나 외부 유료 API를 요구하지 않습니다.

## 이번 작업의 화면

상단에서 **고객 여행 / MD 작업실**을 전환합니다. 전환해도 입력 중인 고객 선택과 기존 고객 일정, MD 편집 상태가 유지됩니다. 로그인·권한 분리가 아닌 로컬 시연용 화면 선택입니다.

### 고객 여행

- 보행 시간·한식 빈도·현지식 선호는 단일 선택 버튼입니다.
- 필수 경험·확인하고 싶은 부담·식사 장소·피할 식재료는 복수 선택 버튼입니다. 식사 장소의 ‘모름’과 구체적인 선택은 함께 선택되지 않습니다.
- 필수 경험을 여러 개 선택하면 모두 예시 일정에 남기고 전후 비교에 표시합니다. 선택만으로 실제 시간·영업 제약을 만족했다고 보장하지 않습니다.
- 선택 요약을 표시하고, 뒤로 가거나 프로필 API에 전송할 때 선택을 보존합니다. 실제 API 필드·스키마는 변경하지 않았습니다.
- 계단·긴 보행·대기·더위 조건은 추가 확인 요청으로 표시합니다. 해당 조건의 실제 평가나 경로 조회는 연결하지 않았습니다.

### MD 작업실

- 3일짜리 독립 예시 초안을 편집합니다. 고객 프로필로 만든 기존 다박 일정과는 별도입니다.
- 장소 검색·종류 필터, 날짜 선택, 장소 담기·삭제, 순서 변경, 날짜 이동, 직전 편집 실행 취소(최대 30회)를 제공합니다.
- 장소 선반에서 일정의 삽입 위치로 드래그하거나 ‘담기’ 버튼을 누릅니다. 일정 내 드래그·위아래 버튼으로 순서를 바꾸고, 날짜 이동은 선택 메뉴로 합니다. 모바일·키보드 사용자는 버튼과 메뉴로 동일한 편집을 수행합니다.
- 같은 날 같은 장소를 중복 추가하거나 중복된 날짜로 이동하지 않습니다. 날짜별 반복 방문은 허용합니다.
- 지도는 선택 날짜의 대략적 장소 위치와 방문 순서를 표시하며 실제 길찾기가 아닙니다. 장소 정보 패널에서 미확인 정보와 확인할 행동을 안내합니다.
- 예시 내부 보행량 합계와 식사·휴식 개수를 원본 대비 표시합니다. 휴식을 추가해도 보행량이 줄었다고 계산하지 않습니다. 장소 사이 이동과 실제 접근성은 미반영입니다.
- ‘고객 미리보기’는 **현재 MD 편집 데이터**를 읽습니다. MD 편집으로 돌아와도 유지되고 HTML 안내서에 같은 방문 순서가 저장됩니다. 가족별 적합도 분석이나 고객 일정 생성으로의 자동 이식은 이번 범위가 아닙니다.
- 상태는 브라우저 메모리에만 보관합니다. 새로고침하면 사라지고 DB·상품 발행·다른 사용자 간 공유는 연결하지 않았습니다.

### 미확인 정보

동선·보행·부담도를 확인하지 못하면 ‘미확인’을 표시하고, **무엇을 확인하지 못했는지 / 누구에게 무엇을 직접 알아봐야 하는지** 안내합니다. MD 작업실, 고객 일정, 미리보기, 다운로드 안내서에도 남깁니다. ‘쉬움’이나 안전 보장으로 치환하지 않습니다. 기존 고객 시연 규칙 결과와 실제 적합도는 구분합니다.

### UI 검토 배경

[Notion UI·UX 아이디어 스케치](https://app.notion.com/p/40db00a36e9b81c1aaf7c57897dc8894). 기존 보라색 토큰·카드 체계를 사용하고, 모바일 레이아웃·키보드 버튼 조작·동작 줄이기 설정을 고려했습니다. 외부 서비스의 화면이나 인증·예약 기능을 복제하지 않았습니다.

## 바꾼 이유

이전 목업은 하루의 규칙 검사 과정을 순서대로 읽는 화면이었습니다. 심사 시연에서는 여행 자체가 먼저 보여야 한다고 판단했습니다. 이번에는 날짜·인원이라는 익숙한 예약 입력으로 시작하고, 그 결과를 여러 날의 여행 일정과 지도에 펼칩니다. 가족의 조건이 어떤 날의 어떤 구간에 영향을 주는지를 일정 안에서 확인합니다.

여행 정보 수정이나 일정 조정은 새 페이지를 차례대로 통과하는 방식 대신 같은 여행을 계속 편집하는 방식입니다. 날짜별 보행량, 위치, 휴식과 필수 경험이 함께 바뀝니다. 전후 비교와 큰 글씨 카드는 여행 전체를 설명하는 마무리입니다.

## 세 가족

| 사례 | 실제 여행 인원 | 기본 기간 | 일정에서 다루는 차이 |
| --- | --- | --- | --- |
| 부모님만 여행 | 아버지 72세·어머니 68세, 2명 | 3박 4일 | 자녀의 원격 준비, 사찰 방문을 유지하며 긴 보행 조정 |
| 3대 가족 | 조부모 71세·67세, 부모 2명, 초등학생 9세, 총 5명 | 4박 5일 | 세대 간 속도 차이, 필수 해변 경험·체험·휴식 |
| 초등학생 자녀가 있는 핵가족 | 부모 2명, 자녀 8세·11세, 총 4명 | 3박 4일 | 고령 프로필을 건너뛰고 공예·수영 등 활동·자유시간 |

고령 동행자는 성인 중 일부로 계산합니다. 인원에 두 번 더하지 않습니다. 나이는 50세 이상 상세 프로필의 입력 기준이고, 50세 이상을 모두 같은 체력으로 취급하지 않습니다. 어린이·청소년은 만 18세 미만으로 받으며 항공 운임의 성인/아동 구분과는 별개인 여행 구성 입력입니다. 항공·숙박 비용은 계산하지 않습니다.

## 시연 순서

1. 랜딩에서 가족 사례 선택.
2. 출발일, 2~5박(3~6일), 성인·자녀·그중 고령 동행자 수 선택. 자녀 나이 입력.
3. 고령 동행자가 있으면 한 분씩 호칭·나이·성별·연속 보행 답변 입력. 없으면 생략.
4. 펼쳐진 버튼으로 필수 경험(복수), 확인할 부담, 현지 음식 선호, 한식 필요도, 피할 식재료·기타 음식, 식사 장소 입력.
5. 생성 후 기본으로 DAY 2 표시. 여행 기간·출귀국 날짜·인원은 상단에서 유지.
6. 날짜 클릭 → 해당 날짜 일정·보행 지표·지도 핀과 방문 순서 변경. `여행 한눈에`에서 도착~귀국 모든 날 확인.
7. 긴 구간에 짧은 관람 코스·중간 휴식을 독립적으로 적용. 필수 장소는 제외하지 않음. 날짜를 바꿔도 다른 날 수정 유지.
8. 장소 카드·지도 번호를 선택하면 함께 강조. 근거와 미확인 정보 펼치기. 모바일에서는 지도 버튼으로 전체 화면 지도 열기, 닫기·Escape 지원.
9. 전체 여행 전후 비교 → 날짜별 큰 글씨 카드(SVG)·전체 안내서(독립 HTML) 실제 다운로드.

여행 정보를 다시 생성하면 이전 일정 수정은 초기화합니다. 새로고침하면 모든 입력과 수정이 초기화됩니다. 서버·브라우저 어디에도 여행·개인정보를 영속 저장하지 않습니다.

## 실제로 연결한 것

- **`POST /api/profile`**: 각 고령 동행자마다 기존 API로 `age`, `gender`, `walking_duration`과 음식 선호 4문항의 필드를 전송합니다. 응답의 연령·성별 평균 보행속도를 사용합니다. 고령 동행자가 없으면 호출하지 않습니다.
- **지도**: 로컬에 포함한 Leaflet 1.9.4와 OpenStreetMap 타일. 지도 핀은 이 목업이 작성한 대략적 좌표이며 Google Places 결과가 아닙니다. Google 리뷰·Places 콘텐츠를 OSM에 표시하지 않습니다.
- **다운로드**: 하루 카드 SVG, 전체 날짜가 포함된 HTML 안내서. 외부 메신저 전송·예약은 없습니다.

프로필 API가 실패하면 건강한 인구 평균을 흉내 내어 계산하지 않고 `walking_speed: null`을 유지합니다. 화면에 `예시 프로필 · API 미연결`을 표시하고 시연 가정 속도 0.8m/s를 사용합니다. 핵가족은 0.9m/s(자녀 없음은 1.1m/s)를 가정합니다.

## 가정과 아직 연결하지 않은 것

- 날짜는 출발일 + 숙박 수로 귀국일을 계산합니다. 현지 숙박과 여행 일수를 구분합니다.
- 낮 비행 예시: 한국 08:30 → 다낭 11:00, 귀국 다낭 16:00 → 한국 22:30. 모든 시각은 해당 도시 현지 시각이며 실제 항공편은 조회하지 않았습니다. 귀국 수속은 14시 이후, 체크인은 14시 이후, 점심은 12시 이후, 저녁은 18시 이후로 배치합니다.
- 숙소는 미케 해변 근처 연박이라는 개념상의 위치입니다. 실제 호텔 상품·객실·시설이 아닙니다.
- 관광지 내부 거리, 짧은 코스 접근성, 이동·관람 시간, 부담 등급은 전부 화면 시연용 가정입니다. 실제 경로·영업시간·계단·승강기·쉴 곳은 미확인입니다.
- 지도 선은 좌표를 잇는 방문 순서입니다. 길찾기·최단 경로·실제 도로·출입구 위치가 아닙니다. OSM 타일을 못 읽어도 핀과 연결선은 유지하고 배경 미연결 표시를 합니다.
- 프로필 API 평균 속도 중 최솟값으로 가족의 내부 보행 시간을 계산합니다. 이는 건강한 인구 평균이며 보행 불편을 보정한 값이 아닙니다. 생활형 답변은 별도의 시연 한도 12/20/40/60/90분(모름 20분)에 반영합니다. 자녀 동반 한도는 25분, 성인만은 40분 가정입니다.
- 쉬지 않고 이어지는 보행은 관광지 내부 보행을 누적합니다. 차량 이동을 확인된 휴식으로 간주하지 않는 보수적인 가정입니다. 식사·숙소·앉는 휴식에서 끊습니다. 휴식 추가는 연속 보행만 끊고 하루 총거리는 줄이지 않습니다.
- 새로 머지된 `src/restaurants`의 4문항 필드와 값은 입력·프로필 요청에 맞췄습니다. 수집기는 아직 HTTP 라우트로 노출되지 않았고 실제 식당 검색은 이 목업에서 호출하지 않습니다. 식당·메뉴·리뷰를 임의의 실제 검색 결과처럼 만들지 않았습니다.
- DB·Scoring AI·LLM 일정 생성·항공·숙소·날씨·상담·예약·부모님 피드백 수집은 미연결입니다. 이 목업을 실제 통합 완료로 보지 않습니다.

## 데스크톱 정보 위계 보완

실무에서 안내·선택 대상·편집 결과를 먼저 읽을 수 있도록 UI를 조정했습니다. 기능과 데이터 흐름은 기존과 같습니다.

- 작업 영역을 중립적인 회색·흰색으로 나누고, 본문과 보조 설명의 글자 크기·대비를 높였습니다. 보라색은 주요 행동과 선택·변경 강조에 사용합니다.
- ‘01 장소 선택 → 02 일정 편집 → 03 변경 확인’으로 영역의 목적을 표시합니다. 작은 구석 문구였던 편집 방법은 일정 위의 안내 블록으로 옮겼습니다.
- 주 행동은 고객 미리보기로 유지하고, 실행 취소·담기·삭제·정렬 등 보조 행동은 낮은 강조와 일관된 크기로 정리했습니다. 모바일 조작 영역은 유지합니다.
- 관광·체험·휴식·식사 아이콘의 색을 구분하되 종류명도 함께 표시합니다. 녹색은 휴식 종류를 뜻하며 검증 완료나 안전 판정이 아닙니다.
- 각 카드의 반복되는 미확인 배지는 중립색으로 낮추고, 직접 확인이 필요한 안내는 황토색 강조와 읽기 쉬운 본문으로 유지했습니다.
- 현재 선택 날짜는 짙은 배경과 명확한 글자 대비로 구분하고, 바뀐 수치에만 추가 강조를 줍니다.
- 고객 입력에서도 설명·질문을 먼저 읽도록 데스크톱 선택 버튼·다음 버튼의 크기를 정리했습니다.

참고한 원칙과 적용 판단:

- [Linear — A calmer interface for a product in motion](https://linear.app/now/behind-the-latest-design-refresh): 핵심 작업과 탐색 UI의 시각적 무게를 다르게 둔다는 원칙을 참고했습니다.
- [IBM Carbon — Button guidelines](https://www.carbondesignsystem.com/building-blocks/core/components/button/guidelines): 주 행동과 보조 행동을 서로 다른 강조 수준으로 표현하는 원칙을 참고했습니다. Carbon 컴포넌트 자체를 도입한 것은 아닙니다.
- [Nielsen Norman Group — Visual Hierarchy in UX](https://www.nngroup.com/articles/visual-hierarchy-ux-definition/): 크기·대비·그룹 구분으로 읽는 순서를 만든다는 설명을 참고했습니다.

위 적용은 반걸음 화면에 대한 디자인 판단입니다. 실제 MD 대상 사용성 테스트를 완료했거나 업무 효율 향상을 측정했다는 뜻은 아닙니다.

보완 후 확인:

- 기존 `check_workspace.py` 전체 통과: 1440·1024·768·390·320px, 실제 드래그·편집·실행 취소·화면 전환·다운로드·동작 줄이기. 추가 안내로 레이아웃 높이가 달라져, 자동 드래그 검사는 화면 안에서 보이는 인접 카드의 이동으로 조정했습니다. 화면 가장자리 자동 스크롤은 이번에 검증하지 않았습니다.
