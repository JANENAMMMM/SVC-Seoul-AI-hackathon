# 일정 엔진 문제점 정리

> 노희윤 · 2026-11-04 · 브랜치 `feat/route-planner`
> 일정 엔진([route_planner.md](route_planner.md))과 자연어 피드백 변환(8장)에서 확인한 문제를 모았다.
> 각 항목에 **어떻게 확인했는지**를 적었다. 확인하지 못한 것은 "미확인"으로 표시했다.

## 확인 방법

| 표시 | 뜻 |
| --- | --- |
| 실행 | 실제로 일정을 돌려서 결과를 확인 (아래 "시험 조건") |
| 코드 | 코드를 읽어서 확인. 일정을 돌려서 재현하지는 않음 |
| 미확인 | 추정. 아직 확인하지 않음 |

**시험 조건:** 다낭 3일, 부모님(아버지 68세, 어머니 65세), 연속 보행 30~60분, 돼지고기 기피, 한식 2~3일에 한 번, 관광지 6곳(한시장·용다리·대성당·미케 해변·호이안 구시가지·호이안 야시장), 데모 식당 데이터(태그 포함), 출발일 없음.

## 일정 엔진

### E1. 날짜 배정이 쏠린다 (3곳 + 1곳)

**증상.** 시내 장소 4곳이 1일차 3곳, 2일차 1곳(미케 해변)으로 갈렸다. 2일차는 09:10~10:10 관광 한 번, 점심 뒤 13:30에 숙소로 돌아온다.

**원인 (실행 + 코드).** 같은 권역 장소를 모으는 단위의 상한이 `권역 용량 × spread_ratio`다.

| 값 | 계산 |
| --- | --- |
| 시내 권역 용량 | 사용 가능 560분 − 왕복 이동 오버헤드 = 540분 |
| 상한 | 540 × 0.55 = **297분** |
| 장소 1곳의 부하 | 체류 60분 + 이동 여유 15분 = 75분 |
| 누적 | 75 → 150 → 225 → **300** (4번째에서 상한을 3분 넘김) |

4번째 장소가 새 단위가 되어 3+1로 갈린다. 배정 뒤에 균형을 맞추는 `_spread_to_empty_days`는 **빈 날이 있을 때만** 동작해서, 이번처럼 날이 비지 않고 쏠린 경우는 손대지 않는다.

**확인한 것.** `spread_ratio`를 0.75나 1.0으로 올려도 낫지 않는다. 시내 3곳이 한 날에 모이고 한시장 1곳이 따로 3일차로 가서 구성만 바뀐다(실행).

**개선 방향.**

| 안 | 내용 |
| --- | --- |
| A | 같은 권역을 나눌 때 남은 날 수에 맞춰 균등 분배 (4곳, 2일이면 2+2) |
| B | 배정 뒤 날짜별 장소 수 차이가 2 이상이면 가장 많은 날에서 하나를 옮기는 균형 단계 (`_spread_to_empty_days` 확장) |
| C | `spread_ratio` 조정은 효과가 없었다 |

### E2. 식당을 순서 확정 뒤에 끼워서 이동이 어색하다

**증상 (실행).**
- 점심 뒤 "택시 10분 → 다음 장소" 표시가 나오는데, 다음 일정이 없거나 몇 시간 뒤이다.
- 1일차 저녁 뒤에 이동이 연달아 둘(19:10 "→ 다음 장소", 19:20 "→ 다낭 시내") 나온다.

**원인 (코드).** `simulate`가 관광지 순서와 시각을 먼저 확정하고, 식당은 `fill_restaurants`가 나중에 채운다. 식당 앞뒤 이동은 식당을 고른 뒤 끼워 넣는 방식이라, **식당 위치에서 다음 장소로 가는 이동이 실제 계산에 반영되지 않는다.** 식당 선택이 순서 탐색에 들어가 있지 않다.

**개선 방향.**

| 방법 | 내용 | 비고 |
| --- | --- | --- |
| A. 시뮬레이션 안에서 식당 선택 | 식사 시각에 도달한 위치에서 식당을 고르고, 식당 위치에서 이동을 이어서 계산 | 변경 범위가 가장 작음. 순서 후보마다 식당 선택을 호출하므로 결과 캐시가 필요(계산 시간은 재 보지 않음) |
| B. 식당 후보 상위 N개를 시뮬레이션으로 비교 | 다음 장소까지의 이동까지 고려한 선택 | 계산량이 N배 |
| C. 식사 자리를 순서 탐색에 포함 | 이론상 최선 | 장소 6개 + 식사 2개 = 8개, 40,320가지 |

**주의 사항.** 날짜를 넘나드는 식당 중복 방지(`used`), 고정 식당(`meal_pins`), 한식 슬롯 규칙이 탐색 중에도 유지돼야 한다.

### E3. 일찍 끝나는 날 빈 시간이 길다

**증상 (실행).**
- 1일차: 관광이 12:10에 끝나고 저녁이 18:00에 고정되어 **13:30~18:00 4시간 반이 빈다.**
- 2일차: 활동이 10:10에 끝나서 **저녁 자체가 없다.** 점심(12:00) 뒤 13:30에 복귀한다.

**원인 (코드).** 저녁이 들어가는 조건이 셋뿐이다(`engine.py` `simulate`).

| 조건 | 1일차 | 2일차 |
| --- | --- | --- |
| 활동이 15:00 이후에 끝남 | X | X |
| 시내에서 편도 45분 이상인 장소가 있음 (바나힐, 호이안, 누이탄타이, 껌탄, 미선) | X | X |
| 한식을 먹어야 하는 날 (2~3일에 한 번 = 1, 3, 5일차) | **O** | X |

일찍 끝나는 날에 비는 시간을 채우거나 줄이는 규칙이 없고, 일정표에도 빈 시간이 표시되지 않는다. 지원님 문서의 "알고 있는 한계"에 같은 내용이 있다(바나힐·누이탄타이 복귀 후 약 2시간 반, 미선은 점심 뒤 저녁까지 5시간 넘게).

**결정이 필요한 것.** 하루 장소가 적은 날에도 저녁을 먹게 할지, 빈 시간에 다른 장소를 옮겨 올지.

### E4. 먼 관광지 날이 12시간이다

**증상 (실행).** 3일차는 09:00 출발, 21:14 복귀(12시간 14분), 난이도 4. 호이안은 다낭에서 편도 53분이다. 호이안 구시가지는 체류 240분이 점심으로 나뉘어 방문이 둘로 쪼개졌다(09:53~12:00, 13:20~15:13). 야시장 개장(17:00)까지 1시간 40분이 빈다.

**원인 (코드).** 야시장이 저녁에야 열어서 같은 권역 낮 일정과 묶인다(`evening` 장소 규칙). 하루 길이에 대한 제한이나 비용이 없다.

**결정이 필요한 것.** 65~68세 기준으로 하루 최대 길이를 정할지, 야시장처럼 저녁 장소를 어떻게 다룰지.

### E5. 기피 재료와 한식이 충돌하면 한식을 못 먹는다

**증상 (실행).** 돼지고기 기피 + 한식 2~3일에 한 번 조건에서 3일차 저녁이 한식이 아닌 일반 식당(Pause and Enjoy)으로 대체됐다. 일정의 `assumptions`에 "조건에 맞는 한식당을 찾지 못해 일반 식당으로 대체했다"고 표시된다.

**원인 (실행 + 데이터).** 호이안 구시가지·야시장 근처 한식당(칠성식당, 윤식당, 압꾸정)이 **모두 `pork` 태그**를 가졌다. 필터가 의도대로 거른 결과다.

**의미.** "돼지고기 기피 + 한식 필요" 조합은 지역에 따라 한식 빈도가 지켜지지 않을 수 있다. 사용자에게 어떻게 보일지는 정해지지 않았다(안내 문구만 있음).

### E6. 하루 순서 탐색이 장소 7개부터 근사다

**코드.** 하루 장소가 6개 이하면 모든 순서를 시뮬레이션해서 위반 수와 비용이 가장 낮은 순서를 고르고, 7개 이상이면 최근접 이웃(가까운 곳부터)이다. 지역과 관광지가 늘면 근사 쪽이 품질의 약점이 된다. 지금 데모(하루 3곳 안팎)는 해당되지 않는다.

### E7. 이동·체류 시간이 추정값이다

**코드.** 이동시간은 직선거리 × 도로 보정(도보 1.2, 택시 1.3) ÷ 35km/h(최소 10분)이다. 체류시간은 60/120/240분 유형별 추정이다. 산길이 많은 곳(바나힐, 하이반 고개)은 직선거리와 실제 차이가 크다. 식당까지 도보 이동은 연속 보행 계산에 넣지 않는다. 지원님 문서에도 있는 한계다.

### E8. 날짜 배정에 목표 함수가 없다

E1, E3, E4의 공통 원인이다. 하루 안의 순서는 `simulate`가 위반 수와 비용(이동, 대기, 늦은 종료)으로 비교하지만, **날짜 배정은 "상한을 넘지 않을 때까지 채우기"뿐**이라 3+1이든 2+2든 같은 값이다.

**방향 (제안).** 하드 제약(권역, 용량, 영업시간, 보행 한도)은 그대로 두고, 그 위에서 날짜별 장소 수 편차, 빈 시간, 하루 총 길이를 비용으로 넣어 고른다. 그래프 라이브러리가 핵심이 아니라 비용 함수를 두는 것이 핵심이다. 지금 규모(장소 6~15개, 3~5일)에서는 E1의 B안 정도로 충분하다.

### 기타 (코드로 확인)

| 항목 | 내용 |
| --- | --- |
| 출발일 없음 | 요일별 휴무를 반영하지 못한다. `assumptions`에 "출발일이 없어 … 휴무를 반영하지 못했습니다"가 붙는다 |
| 영업시간 불명 | 호이안 구시가지·야시장은 영업시간 정보가 없어 가정값(신뢰도 medium)을 쓴다 |

| 없는 명령 | `set_food_pref`, `avoid_ingredient`, `suggest_alternatives` |

## 로직 자체의 한계 (설계상 한계, 코드로 확인)

위의 E항목은 일정에서 드러난 개별 문제이고, 아래는 **로직이 이렇게 짜여 있어서 생기는 구조상 한계**다. 지금 데모 범위에서는 드러나지 않을 수 있지만 지역과 관광지가 늘거나 사용 방식이 달라지면 문제가 된다.

| S1 | **식당이 동선 계산에 들어가지 않는다** | 처리 순서가 `날짜 배정 → 하루 순서·시각 확정 → 식당 채우기`다. 식당은 순서와 시각이 정해진 뒤 그 자리(anchor)에서 고른다. 그래서 식당 위치나 영업시간이 순서 선택에 영향을 주지 못하고, 식당에서 다음 장소로 가는 이동도 실제 위치 기준으로 계산되지 않는다(E2). 식사 시각 창도 고정이다(점심 12:00~14:00, 저녁 18:00~20:00, 식사 60분). |
| S2 | **식당 선택이 슬롯마다 독립적인 탐욕 선택이다** | 끼니 하나씩 "점수 − 0.08 × km"가 가장 높은 식당을 고른다. 다음 장소까지의 이동이나 전체 일정은 보지 않는다. 날짜 순서대로 고르면서 이미 쓴 식당을 제외(`used`)하므로 **앞 날이 좋은 식당을 먼저 가져가고 뒷날은 남은 것 중에서 고른다.** |
| S3 | **식당 후보 조건이 하드 기준이다** | 평점 3.8 미만 또는 리뷰 30개 미만은 제외하고, 반경 3km(없으면 6km), 식당까지 이동 10분 이내, 영업시간 안이어야 한다. 외곽 관광지는 후보가 없을 수 있고, 그러면 한식 슬롯은 일반 식당으로 대체되거나 식당이 비어 "후보 없음"이 된다. |
| S4 | **숙소 기점이 하나다** | 모든 날이 기점 한 곳(기본 다낭 시내)에서 시작해서 돌아온다. 호이안에서 숙박하는 식으로 숙소를 옮기는 일정은 표현할 수 없고, 먼 관광지 날은 왕복 이동이 하루를 길게 만든다(E4). |
| S5 | **권역이 설정에 박혀 있고 권역을 섞지 않는다** | 지역→권역 대응(시내, 남쪽, 서쪽, 바나힐)은 `config.json`에 직접 적혀 있다. 다른 권역 장소는 같은 날 넣지 않아서, 일수가 부족하면 "일수가 부족하거나 권역이 달라 같은 날 배치할 수 없습니다"로 미배치가 된다. 새 지역은 설정을 수작업으로 추가해야 한다. |
| S6 | **날짜 배정이 시뮬레이션보다 먼저, 근사로 이루어진다** | 배정은 `체류시간 + 이동 여유 15분`의 합으로 용량을 어림하고(E1), 실제 시각 계산은 그 뒤 하루 시뮬레이션에서 한다. 어림이 틀리면 장소가 휴무·마감으로 빠지고, 빠진 장소는 같은 권역의 다른 날로 한 번 옮겨 본다. 그래도 안 되면 미배치다. |
| S7 | **프로필 병합이 가장 약한 사람 기준이다** | 여러 명이면 보행 속도는 가장 느린 사람, 연속 보행 한도는 가장 짧은 사람, 한식 필요는 가장 높은 쪽, 현지 음식은 "익숙한 음식" 선호가 한 명이라도 있으면 그쪽을 따른다. 두 분의 차이를 반영해 일정을 나누지 못하고, 한 분이 약하면 모두 같은 제한을 받는다. |
| S8 | **한식 빈도가 단순하다** | "2~3일에 한 번"은 간격 2일(1, 3, 5일차)로 고정이다. "가끔 / 없어도 됨 / 모름"은 한식을 강제하지 않는다. 한식은 하루 한 끼(저녁 우선)만 배치한다. |
| S9 | **이동 수단이 도보와 택시뿐이다** | 도보는 10분 이내일 때만 쓰고, 택시는 평균 35km/h에 최소 10분이다. 버스, 렌터카, 기사 포함 차량은 없다. 비용이나 이동 수단 선호를 반영할 수 없다. |
| S10 | **코스 방식(`short`)을 바꿔도 시간은 그대로다** | "가볍게"는 걷는 시간과 난이도만 줄이고 체류시간은 그대로여서, 하루가 짧아지거나 비는 시간이 늘지는 않는다. 지원님 문서에도 있는 한계다. |
| S11 | **재생성할 때 기존 배치를 고정한다** | 수정하지 않은 날은 이전 배치를 `pins`로 고정해서 그대로 둔다. 안정적이지만, 한 번 정해진 배치(예: 3곳 + 1곳)는 피드백으로 다시 균형을 잡지 못하고 사용자가 장소를 직접 옮겨야 한다. |
| S12 | **엔진이 클라이언트가 넘긴 일정과 `state`를 그대로 믿는다** | `refine`은 넘겨받은 일정과 `state`를 그대로 쓴다. 값이 서로 맞는지 검증하지 않는다. 화면용 API는 여행을 DB에서 꺼내 쓰므로 변조 위험은 작지만, 승인 후 이전 버전으로 복원하는 기능은 없다. |
| S13 | **식당은 미리 수집한 JSON만 쓴다** | 실시간 영업 여부나 혼잡은 반영하지 못한다. 영업시간은 한국어 텍스트만 파싱한다. 식당 파일이 없으면 식당 없이 일정만 만든다. |

### 자연어 피드백 변환

| # | 한계 | 내용 |
| --- | --- | --- |
| SL1 | **한 번에 한 문장만 본다** | 변환기에 이전 대화를 넘기지 않는다. "아까 말한 거 말고", "그거 취소해 줘" 같은 이어지는 말은 이해할 수 없다. |
| SL2 | **명령 9개의 표현력이 낮다** | `swap_restaurant`는 어떤 식당으로 바꿀지 지정할 수 없고(제외 후 엔진이 다시 고름), 하루 안의 순서나 시각("점심 먼저 먹고 시장 가요", "오후에는 쉬어요"), 장소별 체류 시간, 두 날의 장소 맞바꾸기는 명령으로 만들 수 없다. 이런 요청은 `unsupported`로 안내만 나간다. |
| SL3 | **변환기가 보는 일정 정보가 적다** | 일정 요약에는 장소와 식당 이름만 있고 시각, 난이도, 걷는 시간은 없다. "너무 힘들어요"처럼 날짜를 말하지 않는 요청은 어느 날인지 추측하거나 되물어야 한다. |

## 자연어 피드백 변환 (LLM)

### L1. 현재 명령으로 못 하는 요청은 반영되지 않는다

변환기는 정해진 명령 9개 중에서만 고른다. 표현할 수 없는 요청은 `unsupported`로 안내만 나가고 일정은 바뀌지 않는다.

| 요청 예 | 지금 | 필요한 것 |
| --- | --- | --- |
| "해산물은 빼 주세요" | 안내만 | `avoid_ingredient` 명령 |
| "한식 말고 현지 음식으로" | 안내만 | `set_food_pref` 명령 |
| "2일차가 너무 비어 있어요" | 안내만. "한시장을 2일차로 옮겨 주세요"처럼 장소를 지정하면 `move_place`로 처리됨 | 날 사이 균형 명령 (엔진 변경) |
| "다른 식당 추천해 주세요" | 안내만 | `suggest_alternatives` 명령 |

이 목록은 어떤 명령이 먼저 필요한지 정하는 자료로 쓸 수 있다. 명령 추가는 엔진 변경이라 지원님과 협의가 필요하다. 변환기의 도구 스키마는 `EditCommand` 모델에서 자동 생성돼서 명령이 추가되면 따라간다.

### L2. 여행 생성에는 호출 제한과 로그인이 없다

**코드.** 화면용 `POST /api/ui/trips`(일정 생성)에는 호출 제한과 로그인이 없고, 호출할 때마다 DB에 여행 한 건이 쌓인다(소유자 키는 생성한 뒤에 발급된다). 일정 계산에는 Claude를 쓰지 않아 비용은 들지 않지만 서버 계산과 DB 쓰기를 누구나 반복할 수 있다. 호출 제한이 있는 곳은 자연어 해석(Claude)으로, 여행 하나당 시간당 30회다. 서비스로 열기 전에는 인증이나 생성 횟수 제한이 필요하다.

### L3. 변환 결과를 확인받지 않고 바로 적용한다

**코드.** 피드백을 보내면 변환과 적용이 한 번에 일어난다. 변환이 틀려도(예: 다른 날짜로 이해) 일정이 바로 바뀐다. 응답의 `applied_commands`와 `change_summary`로 무엇이 적용됐는지 알 수 있고, 이전 일정을 들고 있으면 되돌릴 수 있다. "이렇게 이해했습니다. 적용할까요?" 단계를 둘지는 정해지지 않았다.

### 기타 (코드로 확인)

| 항목 | 내용 |
| --- | --- |
| 하나라도 틀리면 전부 취소 | 변환된 명령 중 하나가 검증에 실패하면(날짜 범위 밖 등) 나머지가 맞아도 일정을 바꾸지 않는다 (기존 `refine`의 원칙) |
| 입력 길이 | 피드백은 1,000자까지만 쓴다 |
| 명령과 피드백을 같이 보낼 때 | 명령이 있으면 피드백은 무시한다 |
| 의존 방향 | 변환기가 식당 패키지의 `Budget`, 모델 상수를 가져다 쓴다. 일정 쪽이 식당 코드에 의존한다 |
| `review_comment` | 일정 검토 코멘트를 LLM이 채우는 기능은 아직 없다 |
| 테스트 환경 | 로컬 `.env`에 키가 있으면 `feedback`만 보내는 API 테스트가 실제 Claude를 호출한다. 지금은 그런 테스트가 없다 |

## 데이터 (식당 태그)

### D1. 식당 태그는 리뷰에 나온 것만 안다

**실행 (데모 식당 100곳).** 한국어 리뷰가 있는 84곳만 Claude가 판단했고, 리뷰가 없는 16곳은 `unknown`, `[]`이다. 엔진은 태그가 있을 때만 거르므로 **놓친 재료는 걸러지지 않는다.** `nuts`는 한 곳도 확인되지 않았다(없다는 뜻이 아님). `venue_type`이 `unknown`인 곳이 32곳이다.

**영향 가능성.** `seafood` 태그가 43곳이라, 해산물을 피하는 프로필이면 식당 후보가 많이 줄 수 있다.

## 우선순위 제안

| 순서 | 항목 | 이유 |
| --- | --- | --- |
| 1 | E1 + E8 (날짜 배정 균형) | 결과가 가장 눈에 띄게 어색하고, 변경 범위가 작다 |
| 2 | E3, E4 (빈 시간, 하루 길이) | 기준 결정 후 같은 균형 단계에 비용으로 넣을 수 있다 |
| 3 | E2 (식당 앞당기기) | 구조 변경. 시험 구현으로 효과와 계산 시간을 먼저 확인 |
| 4 | L1 (명령 추가) | 실제 피드백을 모은 뒤 필요한 명령부터 |
| 5 | L2 | 서비스로 열기 전에 인증이나 호출 제한 |

각 항목의 담당과 구현 범위는 지원님(엔진)과 협의가 필요하다.
