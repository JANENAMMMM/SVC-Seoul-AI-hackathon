# 일정(동선) 엔진

부모님 프로필과 고른 관광지를 받아 **날짜별 일정표**(관광지·식사·이동·휴식)를 만들고,
피드백을 받으면 **정해진 명령으로만** 일정을 다시 짜는 규칙 기반 엔진이다.
LLM(Claude)은 일정을 직접 쓰지 않는다. 자연어 피드백을 이 엔진의 명령으로 바꾸는 일만 맡는다(8장).

- 브랜치: `feat/route-planner`
- 코드: `src/planner/`, `api/routes/planner.py`
- 테스트: `tests/test_planner_*.py` (99개 통과, 전체 210개)
- 담당: 지원(규칙 엔진·명령 적용기) / 희윤(식당 데이터·LLM 변환) / 재은(난이도 점수) / 천지(UI)

## 1. 전체 흐름

```
프로필(여러 명) ─┐
관광지 목록 ─────┼─► 프로필 병합 ─► 일차 배정 ─► 하루 일정 시뮬레이션 ─► 식당 채우기 ─► 난이도 계산 ─► Itinerary
일수/출발일 ─────┘   (가장 약한      (권역·편차)    (순서·이동·휴식·식사)   (슬롯별 선택)   (재은 모듈)
                      사람 기준)

사용자 피드백 ─► (Claude 변환) ─► EditCommand ─► 검증 ─► state 수정 ─► 같은 엔진으로 재생성 ─► 변경 요약
```

서버는 아무것도 저장하지 않는다. 클라이언트가 이전 일정(`state` 포함)을 다시 보내면 그 위에서 수정한다.

## 2. API

| 엔드포인트 | 용도 |
|---|---|
| `POST /api/planner/plan` | 일정 생성 |
| `POST /api/planner/refine` | 명령(또는 피드백)으로 일정 수정 |

잘못된 입력(없는 관광지, 범위 밖 일차 등)은 `422`. 실행은 `uv run uvicorn api.main:app --reload`.

### 입력 `PlanRequest`

| 필드 | 설명 |
|---|---|
| `travelers` | 프로필 배열(`POST /api/profile` 응답 그대로). 여러 명이면 가장 약한 사람 기준으로 합친다 |
| `place_ids` | 관광지 id (`dad-01` ~ `dad-15`) |
| `days` | 일수 (1~14) |
| `start_date` | 출발일. 있어야 요일별 휴무·영업시간을 반영한다 |
| `start_point` | `{lat, lng}`. 없으면 다낭 시내 기준점(한시장 인근) |
| `day_window` | 하루 활동 시간. 기본 09:00~21:00 |
| `state` | 재생성용 상태(처음엔 비워 둠) |

### 출력 `Itinerary`

- `days[]`: 일차별 `stops[]`, `difficulty`(재은 점수), `total_walk_min`, `max_continuous_walk_min`
- `stops[].type`: `base`(출발/복귀) · `attraction` · `meal` · `move`(도보/택시) · `rest`
- 식사 stop의 `restaurant`: 이름·평점·한식/현지 여부·이동 시간/수단, 그리고 `venue_type`, `ingredient_tags`, `tag_confidence`, `tag_evidence`(있을 때)
- `package`: 일정 전체 난이도 (peak, mean)
- `unscheduled[]`: 못 넣은 관광지와 이유
- `assumptions[]`: **가정·미확인 사항 안내** (UI에서 사용자에게 그대로 보여줄 수 있음)
- `state`: 다음 `refine` 요청에 그대로 다시 보낼 값

## 3. 일정을 만드는 규칙

### 3-1. 프로필 병합
- 보행속도는 동행자 중 **가장 느린 값**, 연속 보행 한도는 **가장 짧은 구간**을 쓴다.
- 보행 지속시간 구간별 한도: 15분 미만 12 / 15~30분 20 / 30~60분 40 / 1~2시간 60 / 2시간 이상 90분. 정보가 없으면 20분(가정, `assumptions`에 표시).
- 한식 필요도는 동행자 중 가장 높은 값. 식사 장소(`venues`)는 모두가 이용할 수 있는 것만 남긴다.

### 3-2. 일차 배정
- 관광지를 권역(시내 / 남쪽(호이안+미선) / 서쪽(누이탄타이 단독) / 바나힐 단독)으로 묶어 같은 날에 배정한다.
- 일수가 남으면 빈 날이 없도록 분산한다(날짜당 비율 상한 0.55).
- 15시 이후에 여는 곳(아시아파크 등)은 같은 권역의 낮 일정 날과 짝지어 저녁에 넣는다.
- 바나힐은 하루 단독, 점심은 현장 뷔페로 고정(영업시간상 저녁 불가). 시내에서 먼 관광지(바나힐·호이안·누이탄타이·껌탄·미선)가 있는 날은 활동이 15시 전에 끝나도 **저녁을 항상 배정**한다(3-6 참고).

### 3-3. 하루 일정
- 장소 6개 이하는 모든 순서를 탐색해 `이동 + 대기 + 패널티`가 가장 작은 순서를 고른다.
- 영업시간(Google 요일별 / 한국어 텍스트 / 수동 입력)을 확인한다. 일요일 휴무, 대성당 낮 휴게시간 등 반영.
- 매일 **다낭 시내 기준점에서 출발, 복귀**(`base` stop)한다.
- 체류시간은 3단계: `brief` 60분 / `half` 120분 / `long` 240분. 유형별 기본값 + 관광지별 수동 예외(`stay_source: manual_estimate`).
- 관광지 안에서의 보행은 재은님의 방식별(`standard/short/full`) walking 점수를 환산해 쓴다.

### 3-4. 이동수단 (도보·택시만)
- 도보 환산 10분 이하이고 연속 보행 한도 안이면 도보, 아니면 택시.
- 이동 시간은 직선거리 × 도로 보정(도보 1.2 / 택시 1.3), 택시 평균 35km/h, 최소 10분.
- 도보 이동도 연속 보행 시간에 합산되고, 한도에 닿으면 휴식(25분)이 들어간다. 식사가 휴식을 대신한다.

### 3-5. 방식(mode) 자동 선택
방식 ID(`standard` 표준 / `short` 걷기·오르기를 줄인 코스 / `full` 가장 많이 도는 코스)는 재은님 데이터(`visit_modes_v2_1.json`)의 정의를 그대로 쓴다. `short`의 실제 이름은 관광지마다 달라서(예: 오행산 "엘리베이터·사원 일부", 한시장 "1층만 짧게") 일정의 `mode_name`과 안내문에는 이 **장소별 이름**을 쓴다.

체력이 낮은 프로필(연속 보행 한도 20분 이하 또는 보행속도 1.0m/s 미만)이면 걷기 부담이 큰(walking 6 이상) 관광지를 `short` 방식으로 자동 전환하고 "보행 한도가 짧아 오행산은 '엘리베이터·사원 일부' 코스로 잡았습니다."처럼 안내한다. 방식을 바꿔도 체류시간은 그대로이고 걷는 시간과 난이도만 달라진다.
하루 난이도(재은님 `calculate_package`)가 상한 7을 넘으면, 사용자가 방식을 직접 고르지 않은 관광지 중 부담이 가장 큰 곳부터 `short`로 바꿔 상한 안에 들이고 `assumptions`에 알린다. 사용자가 고른 방식은 바꾸지 않는다.

### 3-6. 식당 선택
후보 필터 → 점수 순으로 고른다.

| 단계 | 규칙 |
|---|---|
| 제외 | 호텔·패스트푸드·카페 등 제외 유형, 평점 3.8 미만, 리뷰 30개 미만 |
| 영업시간 | 식사 시각에 열려 있어야 함(정보 없으면 `hours_unknown`으로 표시) |
| 거리 | 관광지에서 이동 10분 이내, 반경 3km → 없으면 6km |
| 해산물 | 해산물을 피하면 해산물 유형 제외 |
| 태그 | `ingredient_tags`가 피하는 재료와 겹치면 제외, `venue_type`이 프로필 `venues`에 없으면 제외 (태그가 없으면 거르지 않음) |
| 한식 | 한식 슬롯은 JSON 값만 신뢰한다. `is_korean_final`(Claude 재판정 결과)이 있으면 그것을, 없으면 `is_korean`을 쓴다 |
| 점수 | `score − 0.08 × 거리(km)`, 현지 식당은 취향에 따라 ±0.15 |

- 점심 12:00~14:00 시작, 저녁 18:00~20:00 시작, 식사 60분. 식당 왕복 이동은 식사 슬롯 안에 들어간다.
- 저녁 슬롯은 아래 중 하나일 때 생긴다.
  - 마지막 활동이 15:00 이후에 끝나는 날
  - 그날 한식이 필요한 날
  - **시내 기준점에서 45분 이상 걸리는 관광지가 포함된 날**(`config.json`의 `meal.dinner_always_if_base_travel_min_at_least`). 활동이 언제 끝나든 저녁을 넣는다. 권역 이름이 아니라 이동시간으로 판단하므로 관광지가 추가돼도 자동 적용된다. 현재 대상은 바나힐(47분)·호이안 구시가지(53분)·호이안 야시장(54분)·누이탄타이(55분)·껌탄(55분)·미선(78분)이다. 하이반 고개(39분) 이하는 시내 권역으로 보고 대상이 아니다.
  - 저녁 장소: 바나힐·누이탄타이는 시내로 복귀한 뒤 18:00 이후에 배정하고, 호이안·껌탄·미선은 마지막 관광지 근처에서 먹고 돌아온다.
- 그 외에는 활동이 15시 전에 끝나면 저녁 슬롯이 없다(점심만 배정).
- 한식 빈도: `daily`면 매일 저녁, `every_2_3_days`면 1·3·5일차 저녁.
- 한 번 정해진 식당은 `state.meal_pins`로 고정되어 재생성해도 유지된다.

## 4. 피드백 재생성

엔진은 아래 **닫힌 명령 집합**만 받는다. `/refine`에 `commands`를 직접 보내도 되고, `feedback`(자연어)만 보내면 서버가 Claude로 이 명령들로 바꿔서 적용한다(8장).

```json
POST /api/planner/refine
{ "itinerary": { ... 이전 응답 ... },
  "commands": [ { "op": "swap_restaurant", "day": 2, "meal": "lunch" } ],
  "feedback": "자연어 원문(선택). commands가 없을 때만 명령으로 변환된다" }
```

| `op` | 필드 | 동작 |
|---|---|---|
| `lighten_day` | `day` | 그날 관광지를 모두 `short`(장소별 이름의 줄인 코스) 방식으로 바꿈 |
| `add_place` | `place_id`, `day?` | 관광지 추가 |
| `remove_place` | `place_id` | 관광지 제거 |
| `move_place` | `place_id`, `day` | 다른 날로 이동(고정) |
| `set_mode` | `place_id`, `mode` | 관광 방식 변경 |
| `more_korean_meals` | - | 한식 빈도를 한 단계 올림 |
| `set_pace` | `pace` (`slower/normal/faster`) | 보행 한도·하루 용량 배율 변경 |
| `swap_restaurant` | `day`, `meal` | 그 끼니 식당을 제외하고 다시 선택 |
| `adjust_walk_limit` | `direction` (`more/less`) | 연속 보행 한도를 한 단계(12/20/40/60/90) 조정 |

규칙
- **전부 성공하거나 전부 실패**한다. 하나라도 잘못되면 일정은 그대로 두고 `clarification`에 되묻는 문장을 담아 돌려준다.
- 응답: `itinerary`(새 일정), `applied_commands`, `change_summary`(무엇이 바뀌었는지), `clarification`.
- 명령 없이 자연어만 오면 변환기가 명령으로 바꿔 적용한다. `ANTHROPIC_API_KEY`가 없으면 "LLM 변환이 연결되지 않았다"는 안내(`NO_LLM_MESSAGE`)를 돌려준다.
- 변환 결과 중 명령으로 만들 수 없는 요청(`unsupported`)과 되묻는 질문은 `clarification`에 담긴다. 일부만 변환되면 가능한 명령은 적용되고 `clarification`에 나머지가 안내된다.
- 아직 없는 명령: `set_food_pref`, `avoid_ingredient`, `suggest_alternatives`. 이런 요청은 변환 단계에서 `unsupported`로 안내된다.

## 5. 데이터 파일

| 파일 | 내용 | 출처 |
|---|---|---|
| `src/planner/config.json` | 모든 파라미터(보행 한도, 식사 시각, 권역, 가중치 등) | 지원 (가정값 다수) |
| `src/planner/attraction_profile.json` | 관광지 유형·권역·체류 단계 | 지원 |
| `src/planner/attraction_hours.json` | 수동 영업시간(아시아파크 15:00~22:00은 팀 확인) | 지원 |
| `src/planner/stay_config.json` | 체류 3단계 시간·유형별 기본값 | 지원 |
| `data/scoring/attractions.json` | 관광지 좌표·난이도 점수 | 재은 |
| `data/restaurants/restaurants_danang.json` | 식당 데이터 | 희윤 |

식당 파일 경로는 환경변수 `RESTAURANTS_JSON`으로 바꿀 수 있다. 파일이 없으면 식당 없이 관광지 일정만 만든다.

### 식당 JSON에서 엔진이 쓰는 필드

| 필드 | 용도 |
|---|---|
| `place_id`, `name`, `lat`, `lng` | 기본 정보 |
| `primary_type` | 제외 유형·해산물 판별 |
| `rating`, `rating_count`, `score` | 품질 필터와 점수 |
| `is_korean_final` (없으면 `is_korean`), `is_local` | 한식 슬롯, 현지 취향 가점. `is_korean_final`만 있는 파일도 된다 |
| `opening_text` | 요일별 영업시간 |
| `pinned` | 관광지 내부 고정 식당(바나힐 뷔페) |
| `venue_type` | `restaurant` / `street_food` / `unknown` (신규, 합의됨) |
| `ingredient_tags` | `pork/seafood/dairy/nuts` 중 리뷰로 확인된 것. **없으면 `[]`** (신규) |
| `tag_confidence`, `tag_evidence` | 신뢰도와 근거. 거르는 데는 쓰지 않고 사용자 설명용으로 전달 (신규) |

신규 필드가 없는 옛 JSON도 그대로 동작하고, 이때는 `assumptions`에 안내가 붙는다.

## 6. 알고 있는 한계

- **이동 거리는 직선거리 추정**이다(실제 길찾기 API 아님). 거리가 먼 구간은 오차가 클 수 있다.
- 체류시간은 유형별 추정값이다. 관광지별 실측이 아니다.
- 식당까지 도보 이동은 연속 보행 계산에 넣지 않았다(식사로 끊기는 짧은 구간이라 단순화).
- `ingredient_tags`는 리뷰에 나온 재료만 담는다. **태그가 없다고 해당 재료가 없다는 뜻이 아니다.** 일정에 "주문 시 확인 필요" 안내가 붙는다.
- `avoid_other`(직접 입력한 기피 재료)는 식당 선택에 반영하지 않는다(안내만 표시).
- 보행 한도, 휴식 25분, 식사 시각 등 `config.json` 값의 상당수는 가정값이다.
- 실제 식당 데이터로 돌려 보면 어색한 선택이 보인다(익숙한 음식 선호인데 인도 음식 점심, 야식 포차 저녁 등). 식당 데이터 정리가 끝나면 다시 확인한다.
- 날 사이 균형(한 곳만 있는 날), 식당에서 다음 장소로 바로 가지 않고 시내를 거치는 이동, 긴 공백 시간은 개선 후보다.
- 먼 관광지 날은 활동이 일찍 끝나면 저녁(18:00)까지 빈 시간이 길다. 바나힐·누이탄타이는 복귀 후 약 2시간 반이고, 미선은 11시대에 끝나 점심 뒤 저녁까지 5시간 넘게 비며 외진 곳에서 저녁을 먹는다. 일정표에는 별도 표시 없이 비어 있다.

## 8. 자연어 피드백 변환 (LLM)

자연어 피드백을 4장의 닫힌 명령 집합으로 바꿔서 `/refine`에 넣는다. **LLM은 일정을 직접 쓰지 않고 명령만 만든다.** 일정은 같은 엔진이 다시 짠다.

```text
feedback ─► FeedbackInterpreter(Claude) ─► commands / unsupported / question
                                              │
                          commands ─► 4장의 검증·적용·재생성 (그대로)
                          unsupported·question ─► clarification
```

### 동작

| 조건 | 결과 |
| --- | --- |
| `commands`가 있음 | LLM을 부르지 않고 명령을 그대로 적용 (피드백 문장은 무시) |
| `commands`가 없고 `feedback`만 있음, `ANTHROPIC_API_KEY` 있음 | LLM이 명령으로 변환한 뒤 적용 |
| 같은 경우인데 키가 없음 | 이전처럼 `NO_LLM_MESSAGE` 안내 |
| 변환된 명령이 하나라도 검증에 실패 (날짜 범위 밖, 없는 장소 등) | 일정 그대로, `clarification`에 이유 |
| 일부만 명령으로 바꿀 수 있음 | 바꿀 수 있는 것은 적용하고, 나머지는 `clarification`에 안내 |
| 명령이 하나도 안 나옴 (모호하거나 지원하지 않는 요청) | 일정 그대로, `clarification`에 질문 또는 사유 |
| Claude 호출 실패·예산 초과 | 일정 그대로, "피드백을 해석하지 못했습니다" 안내 (서버 에러로 죽지 않음) |

### LLM이 돌려주는 것

도구 `record_commands`를 한 번 호출해서 세 가지를 돌려준다.

| 필드 | 의미 |
| --- | --- |
| `commands` | 변환된 명령 (4장의 9개 중에서만) |
| `unsupported` | 현재 명령으로 표현할 수 없는 요청. 억지로 다른 명령에 끼워 맞추지 않고 그대로 알려준다. 예: 특정 재료를 피하고 싶다, 비는 날을 채워 달라, 식당을 추천해 달라 |
| `question` | 날짜·장소·끼니가 분명하지 않을 때 되묻는 한 문장 |

- 도구 스키마는 `EditCommand` 모델에서 자동으로 만든다(`src/planner/feedback.py`의 `command_schema`). 명령이 추가되면 스키마도 따라간다.
- LLM이 돌려준 명령도 pydantic으로 다시 검증하고, 형식이 틀린 명령은 `unsupported`로 옮긴다.

### Claude에 보내는 정보

- 보냄: 피드백 문장(최대 1,000자), 현재 일정 요약(날짜별 관광지 이름·id, 끼니별 식당 이름), 일정에 없는 관광지 목록(이름·id)
- 보내지 않음: 식당 리뷰, 부모님 프로필 원문
- 결과는 저장하지 않는다.

### 모델과 비용

- Claude Haiku 5.5, effort low, 요청당 호출 1회, 웹 검색 없음
- 예산 상한은 인스턴스(요청)마다 $0.5, 넘으면 호출하지 않고 안내를 돌려준다
- 실측: 문장 1개 호출 추정 약 $0.0003

### 확인한 것

- 실제 Claude 호출 1회로 확인: "첫째 날은 좀 덜 걷게 가볍게 해주세요" → `lighten_day`(1일차) → 엔진 재생성 → 1일차 난이도 4에서 3으로 내려감 (다낭 3일, 아버지 68세 1명 기준 입력)
- 테스트 `tests/test_planner_feedback.py` 15개 (가짜 클라이언트, API 호출 없음): 도구 스키마, 응답 읽기, 잘못된 명령, 예산 초과, `refine` 연결, 키 없을 때 기존 안내 유지
- 문장 한 개로만 시험했다. 다양한 표현의 변환 정확도는 아직 확인하지 않았다.

### 알려진 한계

- **현재 명령으로 못 하는 요청은 반영되지 않고 `unsupported`로만 안내된다.** 필요한 명령 후보: 재료 기피 추가(`avoid_ingredient`), 음식 취향 변경(`set_food_pref`), 대안 제안(`suggest_alternatives`), 날 사이 균형 맞추기. 엔진 변경이 필요해서 지원님과 협의한다.
- 하루가 비는 문제(6장)는 명령으로 풀리지 않는다. "2일차에 한 곳 더 옮겨 주세요"처럼 장소를 지정하면 `move_place`로 처리된다.
- 변환은 매번 조금 다를 수 있다. 결과를 보여줄 때는 `applied_commands`와 `change_summary`로 무엇이 적용됐는지 함께 보여준다.
- `ANTHROPIC_API_KEY`는 루트 `.env`에서 읽는다. 키가 없으면 변환 없이 이전 동작을 유지한다.
